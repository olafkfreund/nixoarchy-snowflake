# Intent: the plugin character's halo stays inside its margin with any sans font

## Problem

The plugin character's halo skin overflows the window's 3 px safety margin when the default sans font is DejaVu Sans.

`tests/character_fit.mjs` checks each skin while the character bounces (`poke('happy')`) and rolls (a fidget). The
whole drawing must stay inside 3–337 × 3–457 of the 340 × 460 window (`:367`). The halo's measured bounds:

| Where | Font (`fc-match sans-serif`) | Halo bounds (left, top, right, bottom) |
| --- | --- | --- |
| p620 | Noto Sans | `8.47, 3.45, 331.74, 326.41`, passes |
| GitHub `ubuntu-latest`, run `43573982762` | DejaVu Sans | `9.73, 2.92, 331.51, 325.45`, top 0.08 px past the margin |

- **The rest of the page doesn't move:** the weather boxes match to 0.01 px on both machines.
- **The halo's own size changes:** about 1.5 px narrower and 0.4 px shorter with DejaVu, and shifted. So something
  that depends on the font changes how the halo is scaled or placed.
- **Speed isn't the cause:** slowing Chromium's CPU 4× on p620 still passes.

DejaVu Sans is a common default (Debian, Ubuntu, many minimal NixOS setups), so real users see the halo clipped at
the top edge. The check is also what keeps the CI PR for #63 (#89) red: its `fit-slow` job fails on exactly this
case.

## Proposed outcome

- The halo stays inside the margin during the bounce and the roll, with Noto Sans and with DejaVu Sans.
- `test_character_fit` passes on p620 and on GitHub's runner, so #89's `fit-slow` job goes green.
- No other skin or look moves. The other fit checks still pass.

## Affected users and systems

- Anyone running the companion whose default sans font isn't Noto, in practice DejaVu.
- The character drawing code in `app/` (the skin accessories) and possibly its CSS.
- CI (#89). No host config and no deploy, beyond the usual companion update afterwards.

## Constraints

- **Fix the app, not the test:**
  - the bound at `tests/character_fit.mjs:367` stays as it is
  - CI doesn't switch fonts to hide the overflow
  - a measurement isn't rounded to make it pass
- **Find the cause first.** Shrinking the halo by a pixel until it fits is not a fix if a font still changes its size.
- **The look doesn't change visibly** on p620 (Noto): no different halo shape or position a user would notice.
- Browser checks run only in headless Chromium with `--disable-gpu` (a GPU Chrome hung p620's AMD GPU twice).
- To measure with DejaVu on p620, use a test-only fontconfig in the browser's environment, never the desktop's font
  settings.

## Open questions

- What ties the halo's size to the font: an `em`-based size, text in the SVG, or layout around the accessory? The
  spec finds out by measuring.
- Should the fit check also run with DejaVu on p620, not only in CI? The spec decides, after the cause is known.
