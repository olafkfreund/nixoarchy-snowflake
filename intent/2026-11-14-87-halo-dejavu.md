# Intent: the plugin character's halo stays inside its margin on every machine

## Problem

The plugin character's halo skin breaks the window's 3 px safety margin on GitHub's runner, where the default sans
font is DejaVu Sans. On p620, where it is Noto Sans, the same check passes.

`tests/character_fit.mjs` checks each skin while the character bounces (`poke('happy')`) and rolls (a fidget). The
whole drawing must stay inside 3–337 × 3–457 of the 340 × 460 window (`:367`). The halo's measured bounds:

| Where | Font (`fc-match sans-serif`) | Halo bounds (left, top, right, bottom) |
| --- | --- | --- |
| p620 | Noto Sans | `8.47, 3.45, 331.74, 326.41`, passes |
| GitHub `ubuntu-latest`, run `43573982762` | DejaVu Sans | `9.73, 2.92, 331.51, 325.45`, top 0.08 px past the margin |

- **The rest of the page doesn't move:** the weather boxes match to 0.01 px on both machines.
- **Slowing the CPU doesn't reproduce it:** with Chromium's CPU slowed 4× on p620, the check still passes.

**The cause isn't known yet.** The font is the most visible difference between the two machines, but nothing ties it
to the halo:
- **The halo's geometry is fixed numbers:** the ellipse is `cy:-114, rx:36, ry:6` with a 4 px stroke
  (`app/static/index.html:1293`), with no text and no `em` sizing (Codex review).
- **The halo also floats:** `translate(0, sin(t·1.6)·2.2)` (`:2432`) moves it up and down by 2.2 px, with a period of
  about 3.9 s.
- **The bounds aren't one frame:** the check combines the box of every frame it samples (`character_fit.mjs:358`),
  across a bounce of about 1.4 s and a roll of about 2.6 s.

So the worst bound depends on which float phase the samples happen to catch. It may also be that p620 never samples
the highest point. The measured top, 2.92 px, is past the 3 px margin but still inside the window. Whether a user sees
any clipping is unverified.

The check is also what keeps the CI PR for #63 (#89) red: its `fit-slow` job fails on exactly this case.

## Proposed outcome

- The halo stays inside the margin at its **highest** point of the float, during the bounce and the roll, on every
  machine. That holds by construction, not because of when the check samples it.
- `test_character_fit` passes on p620 and on GitHub's runner, so #89's `fit-slow` job goes green.
- No other skin or look moves. The other fit checks still pass.

## Affected users and systems

- Anyone whose plugin character wears the halo. Which machines show it is part of the open question.
- **The drawing code shared by every character:** `drawSkin` and the frame loop in `app/static/index.html`. The same
  code draws the Settings previews (`miniNixi`, `:1331`), so a geometry change reaches those too.
- **The renderer:** the real window uses WebKitGTK (`app/window.py:397`), while the fit check uses headless
  Chromium. A fix is verified in Chromium; the real window gets a look by eye.
- CI (#89). No host config and no deploy, beyond the usual companion update afterwards.

## Constraints

- **Fix the app, not the test:**
  - the bound at `tests/character_fit.mjs:367` stays as it is
  - CI doesn't switch fonts to hide the overflow
  - a measurement isn't rounded to make it pass
- **Find the cause first.** Moving the halo by a pixel until it fits is not a fix if the cause is still there.
- Diagnostic measurements and a regression check are allowed; changing the acceptance bound isn't.
- **The look doesn't change visibly** on p620 (Noto): no different halo shape or position a user would notice.
- Browser checks run only in headless Chromium with `--disable-gpu` (a GPU Chrome hung p620's AMD GPU twice).
- To measure with DejaVu on p620, use a test-only fontconfig in the browser's environment, never the desktop's font
  settings.

## Open questions

- **What actually differs between the machines?** The spec answers it on one machine (p620), comparing:
  - the halo's highest float point with the bounce and the roll, computed from the geometry
  - the bounds sampled at controlled float phases
  - a run with DejaVu as the browser's font (a test-only fontconfig)

  It also checks which font Chromium renders: the app asks for `"Inter", system-ui, sans-serif`
  (`index.html:20`), so `fc-match sans-serif` alone doesn't say.
- **Should the check sample the float's worst phase on purpose,** so it no longer depends on timing? The spec decides
  once the cause is known.
