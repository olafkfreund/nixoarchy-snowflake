# Intent: a skill for making and sharing Nixi plugins

## Problem

Nixi has a plugin format, but nothing walks someone through building a
plugin, so the owner and other users cannot make or share plugins
without reading Nixi's source.

- **The rules are only in code and long docs.**
  - The manifest, its keys and the sandbox rules are enforced in
    `app/plugins.py`: the keys at `:28–37` and the checks in `_check`
    at `:114–232`.
  - Some rules are easy to break: a network plugin cannot read status
    (`:219–224`), `argv[0]` must be inside the folder (`:225–228`), and
    a phrase that clashes with a reserved one is refused (`:229–231`).
  - These are described only in `docs/GUIDE.md:445–522` and
    `docs/GETTING-STARTED.md:127–145`.
- **There is no template.** The six folders in `plugins/examples/` are
  the only starting points, and each shows one feature: quips, a prop,
  notifications, or a stage program.
- **There is no sharing path written down.**
  - The tools exist: `lib.<system>.mkCompanionPlugin` (`flake.nix:31–33`)
    builds a checked plugin, `services.nixi.companion.plugins` installs
    one, and `plugins.py --check` and `tests/test_plugin_sandbox.py`
    validate them.
  - But no guide says "make a repo, add a flake output, and others add it
    as an input".
- **No skill exists.** Claude Code on the owner's hosts has a `nixi` skill
  for beginner how-to questions, but none for authoring Nixi plugins.
  `omarchy-make-plugin` is about Omarchy, not Nixi.

## Proposed outcome

- **A `nixi-plugin` skill.** Claude Code (or any user reading it) can take
  someone from an idea to a working, checked, shareable plugin:
  - choose the kind: quips, prop, character, notifications, reactions, or
    a stage program;
  - scaffold it from a template;
  - fill in `plugin.json` within the sandbox rules;
  - check it with `plugins.py --check`, and run it through the sandbox
    locally;
  - install it with `services.nixi.companion.plugins` or the folder
    `~/.local/share/nixi-companion/plugins`;
  - publish it as its own repo and flake, which others add as an input.
- **A copyable template** in `plugins/template/` with a manifest, README,
  LICENSE and a minimal stage `run`. It passes `--check`.
- **Installation:**
  - Anyone who clones the repo has the skill in the repo.
  - The owner gets it on p620 and razer through nixos_config's existing
    `~/.claude/skills` wiring.
- **The skill stays current.** A test fails if the skill names a manifest
  key or a `reads` value that `plugins.py` does not accept, so it cannot
  drift from the code.
- `docs/GUIDE.md` links to the skill.

## Affected users and systems

- **This repo:**
  - `skills/nixi-plugin/SKILL.md` and its references;
  - `plugins/template/`;
  - a test;
  - `docs/GUIDE.md` and `README.md`.
  - No change to `app/plugins.py`, so the plugin sandbox tests are not
    affected.
- **nixos_config:** a link from the skill into `~/.claude/skills` on p620
  and razer.
- **Other Nixi users:** they gain a guide. Nothing changes at runtime.

## Constraints

- **Document today's plugin API (`api: 1`) only.** No new capabilities.
  WhatsApp (#126) is built in, not a plugin.
- **The template must pass `plugins.py --check`** and build with
  `mkCompanionPlugin`.
- **The skill must not suggest weakening the sandbox:** no `network` with
  `reads`, and no paths outside the folder.
- **Follow the skill format** used under `~/.claude/skills`: frontmatter
  with `name` and `description`.
- **p510 is not changed.** Agents never commit, push or deploy.

## Open questions

1. **Where the skill lives.** In this repo under `skills/nixi-plugin/`
   (proposed, so it ships with the code it describes), or in nixos_config?
2. **The template's license.** MIT, like the examples? Proposed: yes.
3. **A plugin index.** Should there be a list of shared plugins (a
   `PLUGINS.md`, or GitHub topic `nixi-plugin`)? Proposed: the GitHub topic
   only, named in the skill. No index to maintain.
