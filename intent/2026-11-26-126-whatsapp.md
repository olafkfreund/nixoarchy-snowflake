# Intent: WhatsApp in Nixi: look up, read, answer and send files

## Problem

Nixi handles the phone (texts, missed calls and calls) but not WhatsApp.
WhatsApp is where most of the owner's personal messages are.

- **Nixi cannot open a WhatsApp chat.**
  - Today a WhatsApp Web notification is only classified as chat
    (`app/server.py:3523`).
  - Nixi has no client, cards, phrases or setting for WhatsApp, so it
    cannot look up, read, answer or send files.
- **The suggested backend is unsafe as shipped.** The owner suggested
  `lharries/whatsapp-mcp` (MIT). Codex and agy reviewed it read-only on
  2026-11-26, at commit `7d6a06d`; line numbers below are for that commit.
  Both found:
  - **An open REST API.** It binds `:8080` on all interfaces, with no
    authentication, for any client that can reach the port
    (`whatsapp-bridge/main.go` L679–785, L898–909).
  - **Any file can be sent.** `send` uploads any `media_path` the process
    can read (L234–286).
  - **Downloads can land outside their folder.** The path is built from the
    file name the sender chose (L375–405, L557–655).
  - **Message text in the logs.** Message text and send requests go to
    stdout, so under a service they would land in the journal (L454–469,
    L695–710, L1056–1079).
  - **Readable stores.** The stores are created 0755 and 0644, subject to
    the umask. They hold the device keys and a plaintext message archive.
  - **An outdated WhatsApp library.** whatsmeow is pinned to March 2025.
    Open PR #402 reports "Client outdated (405)" before pairing. Issue #382
    reports that media downloads fail with 403 because of how the bridge
    builds the URL.
  - **Little maintenance.** The bridge code last changed on 2025-04-06.
  - **The lethal trifecta.** The Python MCP server gives a model private
    data, untrusted incoming text and a send tool together. The upstream
    README warns about this.
- **The plugin API offers no route to a local bridge or a send flow.** Stage
  plugins run in a sandbox that withholds the runtime directory and the
  home folder (`app/plugins.py:654`). They can only fill a card from facts,
  gauges or headlines.
- **Nixi does not load MCP servers.** The lean Claude launch uses
  `--strict-mcp-config` (`app/server.py:6784–6785`).

## Proposed outcome

On p620 and razer, with WhatsApp turned on in Settings:

- **Pairing.** The owner scans a QR code shown on a Nixi card. Each host
  becomes its own linked device on the owner's number.
- **Look up.** The owner can say or type "WhatsApp Anna" or "my WhatsApp
  chats", in English, Norwegian or Polish. Nixi finds the contacts and
  chats, with a pick card when several match.
- **Read.** Recent chats show on a card, and a chat's messages on a thread
  card. Text and names are shown, never spoken.
- **Summarise or suggest, only when asked.** This works on one chat the
  owner has opened:
  - "Summarise" or "suggest a reply" sends that chat's recent messages to
    the model, capped in size and marked as untrusted.
  - The call has no tools. Its answer only fills a card or the editable
    draft.
- **Write and answer.**
  - "Reply to Anna on WhatsApp", or typing into a draft, gives a draft card
    that names the recipient.
  - **Only a real click sends.** Voice, keys and the model cannot.
  - If the result of a send is unknown, Nixi says so and does not offer to
    send again.
- **Send a file.**
  - The owner picks a file with the file chooser or by dragging it in.
  - The card shows the recipient, the file name and the size, and a click
    sends it.
  - Only a file picked this way, and bound to that card, can be sent.
- **Download a file.** With a click, a received file is saved to
  `~/Downloads/WhatsApp/`. It never overwrites an existing file.
- **New messages.**
  - A card offers to open the chat in Nixi, following the same quiet rules
    as phone cards: not while locked, in a meeting, on a call, in Do Not
    Disturb, or while drafting (`app/server.py:8083`).
  - When `notify_details` is off, no names or previews are shown.
- **Off means off.** Turning WhatsApp off:
  - stops the bridge;
  - drops drafts, staged files and WhatsApp cards;
  - keeps no new data.

  "Unlink and forget" also deletes the bridge's stores.
- **Clear messages when it can't work**, separately for each cause:
  - not paired;
  - the bridge is down;
  - the link has dropped and needs relinking (WhatsApp unlinks a device
    when the phone has been offline about 14 days);
  - a send failed;
  - a send's result is unknown.

## Affected users and systems

- **This repo:**
  - a WhatsApp bridge. The owner chose a hardened fork of the lharries Go
    bridge, MIT with attribution. The spec compares it with a minimal bridge
    written on current whatsmeow, and picks the smaller safe one;
  - `nix/` packaging and a flake output. This adds Go to the flake and a
    recurring task: update whatsmeow and its hash whenever WhatsApp changes
    its protocol;
  - the Nixi server: client, cards, endpoints, the draft and send flow, the
    tool-less summary call and the guards;
  - `app/quick.py`, `app/lang/{en,nb,pl}.json` and
    `app/static/index.html`;
  - tests and docs.
- **nixi-nixarchy:** the bridge send policy (`bridge/send-policy.js`). It is
  the twin of `_FLUX_RE` (`app/server.py:962–968`) and must get the same
  WhatsApp rule. Agent traffic in Nixi mode goes through that bridge
  (`docs/GUIDE.md:10`).
- **nixos_config:** a service for the bridge on p620 and razer, and the
  companion bump. p510 is not touched.
- **The owner's WhatsApp account:** two new linked devices, out of the four
  WhatsApp allows.

## Constraints

- **Local-only bridge.** It listens only on a Unix socket under
  `$XDG_RUNTIME_DIR`, with a token. Never on TCP.
- **Private storage.** The state directory is 0700, with umask 077. No
  message text, names or QR codes go into any log.
- **Files.**
  - The bridge sends files only from Nixi's staging folder. Staged files are
    regular files (no symlinks), with a size limit. They are deleted when
    sent, cancelled or expired, and on start.
  - Downloads use names the bridge generates. The sender's file name is
    display text only.
- **Click-only sending.** Drafts are held on the server with one-use tokens,
  and the page checks for a real pointer event. This is the same as
  `phone_send` (`app/server.py:8040`), `click_ok` (`app/server.py:87`) and
  the trusted-click check in `index.html`.
- **Uncertain sends.** An unknown send result is never retried, and the
  draft is not re-armed. Only "definitely not sent" re-arms it, as
  `NotSent` does for the phone (`app/server.py:8056–8059`).
- **Agent separation, honest version.** The bridge runs as the desktop
  user, and so does the coding agent. A 0700 socket does not keep the agent
  out. So:
  - Nixi gives the model no socket, token or send path. Commands that reach
    the bridge or read its stores need a click, under the same rule in both
    places: `app/server.py` and nixi-nixarchy's send policy.
  - Chat text goes only to the tool-less call, only when the owner asks,
    and only for one chat, capped.
  - The leftover risk (a hand-written script run by the agent) is the same
    as for Flux today. The spec states it, and Open question 6 asks the
    owner to accept it.
- **What may leave the machine.** WhatsApp names and text are never spoken
  by ElevenLabs. They never go to the main agent's prompt or session
  history. They never appear on non-WhatsApp cards. When WhatsApp is off,
  not paired, or a phrase is ambiguous, WhatsApp phrases stay local: they
  get an answer card and are never passed to Claude.
- **No rollout before it is proven.** Pairing and a media download must
  work on one host before the second host is enabled.
- **Tests never touch the real account.** Live pairing and sending happen
  only with the owner present.
- **p510 is not changed.** Agents never commit, push or deploy.

## Open questions

1. **Ban risk (pending the owner's confirmation).**
   - Any whatsmeow client is unofficial, and WhatsApp says an unofficial app
     can lead to a temporary or permanent ban.
   - Confirm you accept this for your personal number. Also confirm that 2
     of the 4 linked-device slots are free.
2. **History.**
   - WhatsApp sends some history after pairing.
   - Proposed: keep only what the bridge stores, in its 0700 directory,
     with no extra copy and no backup. Messages deleted in WhatsApp are
     removed when the bridge is told.
   - "Unlink and forget" wipes the store.
3. **Groups.**
   - Proposed: read and download in groups.
   - Text and file sending in direct chats only, in the first version.
   - Group messages raise no new-message card unless the owner is
     mentioned.
4. **Voice notes, captions, edits and deletions.**
   - Proposed: show captions, and show edits and deletions as they arrive.
   - A voice note shows as "voice message", and the owner can download it.
   - No playing or recording in the first version.
5. **Summaries.**
   - The owner chose Claude.
   - Proposed: at most the last 50 messages, or 8,000 characters, of one
     direct chat, as one separate tool-less call. It is never written to
     Nixi's session history.
   - The spec decides whether this call goes through nixi-nixarchy's
     bridge or directly from the server.
6. **The same-user risk.** Accept the Flux-level protection described in
   Constraints? The alternative is running the bridge as its own system
   user, with Nixi reaching it through a small privileged helper. That is
   stronger, but bigger.
7. **Screen capture.** The agent can capture the screen
   (`app/server.py:949`). Should WhatsApp cards be hidden from agent screen
   captures? Proposed: yes.
