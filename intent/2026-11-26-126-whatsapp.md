# Intent: WhatsApp in Nixi: look up, read, answer and send files

## Problem

Nixi handles the phone (texts, missed calls and calls) but not WhatsApp.
WhatsApp is where most of the owner's personal messages are.

- **No WhatsApp at all.** Nixi has no client, stage cards, phrases or
  setting for it. The only link is notifications: a desktop notification
  from WhatsApp Web counts as chat, but Nixi cannot open the chat.
- **The suggested backend is unsafe as shipped.** The owner suggested
  `lharries/whatsapp-mcp` (MIT). Codex and agy reviewed it read-only
  (2026-11-26), and both found the following:
  - **The REST API is open to anyone.** It binds `:8080` on all interfaces
    with no authentication (`whatsapp-bridge/main.go` L679–785, L898–909).
  - **Any file can be sent.** `send` reads any `media_path` from disk
    (L234–286).
  - **A download can write outside its folder.** It builds the path from a
    file name the sender controls (L375–405, L557–655).
  - **Message text ends up in the journal.** The bridge logs it to stdout
    (L454–469, L1056–1079).
  - **The stores are world-readable.** Directories are created 0755 and
    downloads 0644. The stores hold the session keys and the plaintext
    message archive.
  - **The WhatsApp library is too old.** whatsmeow is pinned to March 2025.
    Open PR #402 reports "Client outdated (405)" before pairing, and issue
    #382 reports that media downloads fail with 403.
  - **The code is unmaintained.** Nothing has changed since 2025-04-06.
  - **The MCP layer puts the model at risk.** Its Python server gives a
    model private data, untrusted incoming text and a send tool together,
    which is the "lethal trifecta". The upstream README warns about this.
- **Plugins cannot do this.** Nixi plugins are sandboxed programs that only
  fill cards (`app/plugins.py`). They cannot send, and a network plugin
  cannot read status (`:219–224`). Nixi has no MCP client
  (`--strict-mcp-config`, `app/server.py:6785`).

## Proposed outcome

On p620 and razer, with WhatsApp turned on in Settings:

- **Pairing.** The owner scans a QR code shown on a Nixi card. Each host
  becomes its own linked device on the owner's number, using 2 of the 4
  slots.
- **Look up.** "WhatsApp Anna" or "my WhatsApp chats" finds contacts and
  chats, with a pick card when several match.
- **Read.** Nixi shows recent chats, and a chat's messages on a thread card.
  WhatsApp text and names are shown, never spoken by the cloud voice.
- **Summarise or suggest, only when asked.** On a chat the owner opened,
  "summarise" or "suggest a reply" sends that one chat's text to the model
  as untrusted content. The call has no tools, and its answer only fills a
  card or the editable draft.
- **Write and answer.** "Reply to Anna on WhatsApp", or typing into a
  draft, gives a draft card showing the recipient. **Only a real click
  sends.** Voice, keys and the model cannot send.
- **Send a file.** The owner picks a file (file chooser or drag-and-drop).
  The card shows the recipient, file name and size, and a click sends it.
  Only files picked this way can be sent.
- **Download a file.** With a click, a received file is saved to
  `~/Downloads/WhatsApp/` under a safe name.
- **Notifications.** New WhatsApp messages count as chat. A card offers to
  open the chat.
- **Clear messages when it can't work**, separately for each cause: not
  paired, the bridge is down, the phone has been offline too long, or a
  send failed.

## Affected users and systems

- **This repo:**
  - a vendored, hardened Go bridge (`whatsapp-bridge/`, from
    lharries/whatsapp-mcp, MIT, with attribution);
  - `nix/` packaging and a flake output;
  - a new `app/whatsapp.py`;
  - `app/server.py`: cards, endpoints, the draft and send flow, the
    tool-less summary call, and a guard against the agent's Bash;
  - `app/quick.py`;
  - `app/lang/{en,nb,pl}.json`;
  - `app/static/index.html`;
  - tests and docs.
- **nixos_config:** a user service for the bridge on p620 and razer, and the
  companion bump. p510 is not touched.
- **The owner's WhatsApp account:** two new linked devices.

## Constraints

- **The bridge listens only on a Unix socket** (0700, under
  `$XDG_RUNTIME_DIR`), with a token. It never listens on TCP.
- **The state directory is 0700.**
- **No message text in any log.**
- **The bridge sends files only from Nixi's staging folder.** It writes
  downloads only under names it generates.
- **Sending is click-only,** with server-side drafts and one-use tokens,
  the same as `phone_send` (`server.py:8040`) and `click_ok` (`:87`).
- **The model never gets the socket, the token, or a send path.** Chat text
  goes only to a tool-less call, only when the owner asks, and only for one
  chat. The main agent's Bash is blocked from reaching the bridge, like
  Flux sends (`_FLUX_RE`, `:968`).
- **WhatsApp names and text are never spoken** by ElevenLabs, never put in
  logs, and never put on cards outside WhatsApp's own cards.
- **Tests never touch the real account.** Live pairing and sending happen
  only with the owner present.
- **p510 is not changed.** Agents never commit, push or deploy.

## Open questions

1. **Ban risk.** Any whatsmeow client is unofficial, and WhatsApp says
   unofficial apps can lead to a temporary or permanent ban. The owner
   accepts this risk for the personal number. Confirm.
2. **History.** WhatsApp's first sync after pairing sends some history.
   Should Nixi keep a local archive (the bridge's SQLite, 0700), or only
   recent messages? Proposed: keep what the bridge stores, and add no extra
   copy.
3. **Groups.** Read and reply in groups too, or direct chats only at first?
   Proposed: read groups, and reply only in direct chats in the first
   version.
4. **Voice notes.** Out of scope for the first version (they need ffmpeg)?
   Proposed: yes, out.
5. **Summaries.** Should they use the cloud model (Claude), or a local
   model when one is available? Proposed: Claude, as the owner chose, with
   the chat marked as untrusted.
