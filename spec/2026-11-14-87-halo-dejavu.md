# Spec: the halo stays inside its margin at the top of its float

## What the measurements show

All runs were on p620, in headless Chromium with `--disable-gpu`, from a throwaway worktree. They ran one
`test_character_fit` case each, with bounds printed to two decimals. The halo's float,
`translate(0, sin(t·1.6)·2.2)` (`app/static/index.html:2432`), was pinned to a fixed value for each run.

**The plugin character (`plug:fixture`):**

| Float | Halo bounds (left, top, right, bottom) | Check |
| --- | --- | --- |
| pinned at the top (`-2.2`) | `8.03, 2.80, 331.80, 326.55` | **fails**: top 0.20 px past the margin |
| pinned at the bottom (`+2.2`) | `12.75, 7.56, 327.26, 321.91` | passes |
| moving, as shipped | `9.08, 3.17, 331.88, 326.15` | passes this time, by 0.17 px |

**Every character at the top of the float:**

| Character | Top | Room left |
| --- | --- | --- |
| plug:fixture | 2.80 | −0.20 px |
| devil | 3.03 | 0.03 px |
| terminal | 3.04 | 0.04 px |
| robot | 4.07 | 1.07 px |
| snowflake | 24.13 | 21 px |

**The font Chromium renders:** the page asks for `"Inter", system-ui, sans-serif` (`index.html:20`). On p620,
`fc-match` resolves both `Inter` and `system-ui` to **Liberation Sans**, so that is what the page draws with there,
not Noto (`fc-match sans-serif` was the wrong thing to report in the intent).

**The same machine with DejaVu:** with a test-only `FONTCONFIG_FILE` holding only DejaVu (from the flake's locked
nixpkgs, `dejavu-fonts-2.37`), on the same code, with the float pinned at the top:

| Font | plug:fixture top | devil top |
| --- | --- | --- |
| Liberation Sans (p620's default) | 2.80 | 3.03 |
| DejaVu only | 2.85 | 3.07 |

The difference is 0.05 px, inside the run-to-run spread below.

**So the font isn't the cause.** The overflow happens with either font as soon as the check samples the top of the
float. The halo has no text and no `em` sizing (`:1294`), and the weather boxes, which share the same `<svg>`, match
to 0.01 px across machines. The two CI runs on #89 agree: on the same runner, with the same font, one failed and one
passed.

The halo's top comes from three things together: the float, the bounce and the roll. The check samples only some of
those frames, which is why the result changes from run to run. Pinning the float removes one source. The bounce and
the roll are still sampled on animation frames (`character_fit.mjs:362-364`), so the measured top still varies a
little between runs. See the spread under Design 1.

## Design

### 1. `app/static/index.html`: draw the halo 1 unit lower

- **`:1294`:** the halo ellipse's `cy` goes from `-114` to `-113`. Nothing else in its geometry changes: `rx:36`,
  `ry:6`, stroke width 4.
- **`:2432`:** the float's amplitude becomes a named constant, `const HALO_FLOAT = 2.2`. It is declared at the
  script's top level, next to `let SKIN_PARTS` (`:1207`), so both the frame loop and the test's `ev(...)` can read
  it. It must not go inside `drawSkin`.
  The frame loop uses `translate(0, sin(t·1.6)·HALO_FLOAT)`, so the motion doesn't change. The constant exists so the
  check below can pin the worst phase without copying the number.

**Measured** with `cy -113` and the float pinned at the top:

| Character | Top before | Top after |
| --- | --- | --- |
| plug:fixture | 2.80 | 3.88 |
| devil | 3.03 | 4.69 |
| terminal | 3.04 | 3.97 |

**Repeat runs**, with the fix and the float pinned at the top:

| Character | Top, 3 runs | Spread |
| --- | --- | --- |
| plug:fixture | 3.88, 4.00, 4.00 | 0.12 |
| devil | 4.69, 4.87, 4.22 | 0.65 |
| terminal | 3.97 (1 run) | — |

- **What the guarantee is:** the float's worst phase is fixed. A sampled frame can only miss the bounce's or the
  roll's peak, which makes the top look *lower* on screen than it really gets. So the true worst top is at most the
  smallest value seen.
  - The smallest seen is 3.88, for the plugin character.
  - The widest spread seen is 0.65 px, for Devil.
  - Together they give an estimated true worst of about 3.2 px. That is inside the margin, but not by much.
- **What it is not:** this is measured, not computed from the full animation. A geometric bound over the bounce and
  roll transforms would need the whole frame loop, and the intent's outcome is met by the measurement plus the pinned
  check below.
- **If you want more room:** `cy -112` (2 units, about 2.2 px) would give about 1.9 px. The cost is a shift twice as
  large, so it isn't the default.

**How visible it is:** 1 unit is about 1.1 px in the window. Measured, moving the float by 4.4 units moved the top by
4.76 px. The halo still sits well above the head. With the Devil's numbers, the head anchor `[0,-20]` lifts the halo
to `cy -133`. Its lowest edge, at `-133 + 6 + 2 = -125`, clears the ball's top (`-78`) by 47 units.

The shift is smaller than the float's own 4.4-unit swing, so it doesn't read as a different position.

### 2. `tests/character_fit.mjs`: the halo case checks the worst phase on purpose

Only the `skin halo` case changes. Its code is browser-side text, so `HALO_FLOAT` is read in the page, never by Node:
write `\${-HALO_FLOAT}` or concatenate inside the evaluated string.

- **`on`** (`:339-340`): after `applyLook(...)`, take `const h = SKIN_PARTS.halo`. Replace `h.setAttribute` with a
  wrapper that:
  - turns a `transform` write into `translate(0,-HALO_FLOAT)`
  - counts it in `window.__haloPins`

  Then call `h.setAttribute('transform', …)` once, so the halo is pinned before the first frame.
- **A guard check, before `after` runs.** The case adds one check to the existing loop, after the fit check and before
  `c.after` (`:366-368`). It fails unless all four hold:
  1. `SKIN_PARTS.halo` is still connected to the page (`isConnected`)
  2. its `style.transform` is empty
  3. its `transform` attribute is exactly `translate(0,-HALO_FLOAT)`, built from the constant, not a typed 2.2
  4. `__haloPins` is higher than the one pin from `on`, so the frame loop's writes were really intercepted during the
     case
- **Cleanup always runs:** the guard is a `check(...)`, which records a failure without throwing, so `c.after` still
  runs. `after` runs `applyLook({...LOOK, skin:'none'})`. `drawSkin` clears both roots (`:1288`) and draws a fresh
  group, so the wrapper goes with the old one.
- **The fit bound stays exactly as it is** (`:366-367`): `3 ≤ left, top`, `right ≤ 337`, `bottom ≤ 457`.

This answers the intent's second open question. The check no longer depends on which phase it happens to catch. A
future change that moves the halo up, or makes the float larger, fails every time instead of now and then.

### 3. Nothing else

- No other skin, look or character changes.
- No CI change: #89's `fit-slow` gets a deterministic check once this merges and #89 is rebased.
- The other skins (crown, sprout, bow) don't float, so they have no phase problem.

## Alternatives rejected

- **A smaller float** (`2.2` → `1.4`): this also fits, at about 3.66 px for the plugin character, but it changes the
  motion users see. Moving the halo down by 1 unit changes less.
- **Lowering the halo only for the plugin template:** Devil and Terminal have only 0.03–0.04 px left, so the next
  small change would break them too. The halo is shared, so the fix is too.
- **Damping the float during the bounce and the roll:** more code, in the frame loop, for the same result.
- **Sampling more frames in the check:** it narrows the timing problem but doesn't remove it. Pinning the phase does.
- **Loosening the bound or switching CI fonts:** ruled out by the intent.

## Risks

- **The Settings previews** (`miniNixi`, `:1331`) draw the same halo, so they also show it 1 unit lower. That is
  consistent with the window.
- **The real window uses WebKitGTK:** the geometry is plain SVG numbers, so WebKitGTK draws the same shift. It gets one
  look by eye on p620 after a deploy, which needs the owner's OK.
- **The test wrapper is tied to the frame loop's `setAttribute` call.** If the loop stops calling it, the pin count
  stops rising. If it moves the halo some other way, such as `style.transform`, the guard sees that too. Either way,
  the guard in Design 2 fails, instead of the check quietly going back to sampling.
- **The margin after the fix is about 0.2 px at the estimated worst, not more** (Design 1). A later change that
  raises the halo or the bounce fails the check. That is intended.
- **The pixel snapshot:** `test_snowflake_pixels_match_origin_main` compares the Snowflake page with `origin/main`. It
  draws with `skin:'none'` (`tests/character_fit.mjs:54`), so the halo change can't show up there. The plan still
  runs it, since the whole file runs.
