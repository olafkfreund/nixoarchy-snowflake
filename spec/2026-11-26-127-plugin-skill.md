# Spec: a skill for making and sharing Nixi plugins

## Design

The intent's approved answers:
- the skill lives in this repo;
- the template is MIT;
- shared plugins are found through the GitHub topic `nixi-plugin`;
- installing the skill on p620 and razer is part of #127.

### Files

```text
skills/nixi-plugin/
  SKILL.md                 # the walkthrough (frontmatter: name, description)
  reference/manifest.md    # every manifest key, what it does, its limits
  reference/stage.md       # stage programs: input, output, sandbox, reads feeds
  reference/sharing.md     # repo + flake layout, the flake input on the user side, topic
  reference/private.md     # private characters: local-only path
  template/
    plugin.json            # a stage plugin: id "my-plugin", argv ["run"], network false, no reads
    run                    # executable, prints a valid "facts" stage from its own data
    README.md
    LICENSE                # MIT, notice kept from plugins/examples
    flake.nix              # outputs.packages.<system>.default = nixi.lib.<system>.mkCompanionPlugin { … }
tests/test_plugin_skill.py
```

The skill is under `skills/`, not `plugins/`, so `plugin_dirs()` and
`scan()` never load the template (`app/plugins.py:63–65`, `:320–321`). It is
also outside `legacyPackages.examples` (`flake.nix:37–49`).

### SKILL.md

The skill is short, and links to the reference files for detail. It follows
the intent's walkthrough:

1. **Choose the kind** from a decision table:

   | Kind | Use it for |
   | --- | --- |
   | quips | lines Nixi says |
   | prop | an SVG he wears |
   | character | a whole look |
   | notifications | an app's notifications counted as mail, chat or feed |
   | reactions | `notice`, `music` |
   | stage | a program that fills a card from facts, gauges or headlines |

   It names the example to copy from for each kind, and says plainly that
   none of the examples shows a character or reactions.
2. **Copy the template** (`cp -r skills/nixi-plugin/template my-plugin`).
   Rename the `id`, then edit.
3. **Check:**
   - run `nix develop -c python3 app/plugins.py --check my-plugin`;
   - then do a real run:
     - install it as a folder plugin with `cp -r` into
       `~/.local/share/nixi-companion/plugins/`;
     - in Settings → Plugins, allow it at the consent prompt;
     - say a phrase, and see the card.
   - The sandbox needs `bwrap`, plus `pasta` when `network` is true. The
     skill gives the two error lines to expect when they are missing.
4. **Install** it with `services.nixi.companion.plugins` and
   `nixi.lib.<system>.mkCompanionPlugin`, or keep it as a folder plugin.
5. **Share it:**
   - in its own repo, using the template's `flake.nix`, with the
     `nixi-plugin` topic;
   - users add it as a flake input and list
     `inputs.my-plugin.packages.<system>.default` in
     `services.nixi.companion.plugins`.

It also has a "never" list taken from the checker:
- `network` with `reads`;
- an `argv` path outside the folder;
- symlinks or hard links;
- `videos` (used only by `news`);
- skipping the SVG limits;
- committing a private character.

Each rule cites its line in `plugins.py`.

The skill describes behaviour only. The reference files hold the key
lists, so the test has one place to check.

### Template `run`

- A POSIX `sh` script with no network.
- It prints one JSON stage of kind `facts`, with two rows read from a
  `data.json` next to it. This shows what a plugin may read: its own
  folder.
- It is executable (mode 0755 in git).

### The drift test (`tests/test_plugin_skill.py`)

It is a `unittest` test, like the other plugin tests:

1. `plugins.check_dir(template)` returns no error.
2. The template's `run` is executable. Run through `plugins.run_stage` in
   the sandbox, it returns a valid stage. It is skipped without `bwrap`, the
   same way `test_plugin_sandbox.py` skips. With
   `NIXI_SANDBOX_TESTS=require` it fails instead.
3. Every manifest key, `reads` value, category and reaction written in
   backticks in `reference/manifest.md` and `reference/stage.md` is in
   `plugins.py`'s sets. This catches invalid names, not missing ones.
   The sets are `REQUIRED`, `OPTIONAL`, `PROP_KEYS`, `CHARACTER_KEYS`,
   `STAGE_KEYS`, `CATEGORIES`, `REACTIONS`, `ROUND_FITS` and the `reads`
   values at `:217`.
4. No file under `skills/nixi-plugin/` is a symlink. `template/` has no
   `private` key.

A flake check is added next to `broken` (`flake.nix:78–85`):
`mk { pname = "nixi-plugin-template"; src = ./skills/nixi-plugin/template; }`.
It proves that the template builds with `mkCompanionPlugin`.

- **`README.md`:** a line in the plugins paragraph.

### Rollout (nixos_config)

In `home/development/claude-code-skills/default.nix`, the `localSkills`
gets one entry:
`nixi-plugin = { src = "${inputs.nixi-companion}/skills/nixi-plugin"; to = [ "claude" ]; };`

- It follows the `nixi-companion` input already pinned at `flake.nix:40`,
  so the skill and Nixi update together.
- The spec assumes this home module is active on both p620 and razer. The
  plan's first nixos_config step checks that, and that it is off on p510.
- The rollout follows the usual deploy chain: a PR and bump, `nh os
  switch` on p620, and `just deploy-via-p620 razer`.

## Alternatives rejected

- **The template in `plugins/template/`.** Nixi would load it from a
  checkout (both reviews).
- **Teaching `scan()` to skip `template`.** That changes `app/plugins.py`
  and the sandbox test scope for no gain.
- **The skill in nixos_config.** It would drift from the code it describes,
  and other users would not get it.
- **A new `plugins.py --run` command.** The intent rules out runtime
  changes, and the folder install plus consent is the real path users take.
- **A plugin index file.** It needs upkeep; the topic is enough.
- **A test that the skill mentions every key.** It is too brittle for
  prose. Review covers new features.

## Risks

- **The skill goes stale when the plugin API grows.**
  - The test catches invalid names, not missing ones.
  - Mitigation: a comment in `plugins.py` next to `OPTIONAL` and
    `STAGE_KEYS`: "update skills/nixi-plugin/reference when this changes".
- **The template's `flake.nix` has no tested build.** It references
  `nixi.lib.<system>.mkCompanionPlugin` as an input. The flake check builds
  the template's folder with the same function, but not through the
  template's own `flake.nix`.
  - Mitigation: the plan runs `nix build` once on a copy of the template
    with a `path:` input, and records the result.
- **Rollout.** A wrong `src` path breaks home-manager evaluation on both
  hosts. The plan builds both hosts' configs before the switch. p510 must
  stay unchanged; the plan checks its closure diff is empty for this
  change.
- **No runtime risk.** `app/` is not changed.

## Verification

- `nix develop -c python3 -B -m unittest tests/test_plugin_skill.py` passes.
- With `NIXI_SANDBOX_TESTS=require` it also passes, which proves the sandbox
  run.
- `nix flake check` passes, including `nixi-plugin-template`.
- A copy of the template with a new `id` installs as a folder plugin on
  p620 and shows its card after consent. This is a manual check, done once
  and recorded in the PR.
- `test_plugins.py` and `test_plugin_sandbox.py` still pass, unchanged.
- After the rollout, `~/.claude/skills/nixi-plugin/SKILL.md` exists on p620
  and razer, and `template/` is next to it. p510 is unchanged.
