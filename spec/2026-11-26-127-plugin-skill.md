# Spec: a skill for making and sharing Nixi plugins

## Design

The intent's approved answers:
- the skill lives in this repo;
- the template is MIT;
- shared plugins are found through the GitHub topic `nixi-plugin`;
- installing the skill on p620 and razer is part of #127.

### Files

```text
skills/nixi-plugin/
  SKILL.md                 # the walkthrough (frontmatter: name, description)
  reference/manifest.md    # every manifest key, what it does, its limits
  reference/stage.md       # stage programs: input, output, sandbox, reads feeds
  reference/sharing.md     # repo + flake layout, the flake input on the user side, topic
  reference/private.md     # private characters: local-only path
  template/
    plugin.json            # a stage plugin: id "my-plugin", argv ["run"], network false, no reads, one unique phrase
    run                    # executable (0755), #!/usr/bin/env python3, prints one static "facts" stage
    README.md
    LICENSE                # MIT, notice kept from plugins/examples
    flake.nix              # only input nixi; packages = mapAttrs (_: l: { default = l.mkCompanionPlugin { pname; src = self; }; }) nixi.lib
tests/test_plugin_skill.py
```

The skill is under `skills/`, not `plugins/`, so `plugin_dirs()` and
`scan()` never load the template (`app/plugins.py:63–65`, `:320–321`). It is
also outside `legacyPackages.examples` (`flake.nix:37–49`).

### SKILL.md

The skill is short, and links to the reference files for detail. It follows
the intent's walkthrough:

1. **Choose the kind** from a decision table:

   | Kind | Use it for |
   | --- | --- |
   | quips | lines Nixi says |
   | prop | an SVG he wears |
   | character | a whole look |
   | notifications | an app's notifications counted as mail, chat or feed |
   | reactions | `notice`, `music` |
   | stage | a program that fills a card from facts, gauges or headlines |

   It names the example to copy from for each kind, and says plainly that
   none of the examples shows a character or reactions.
2. **Copy the template** from the `template/` folder next to `SKILL.md`. Use
   `cp -rL --no-preserve=mode` into a fresh folder, then `chmod +x run`. This
   dereferences Home Manager's per-file links, which the checker rejects
   (`app/plugins.py:327`, `:1039`). Rename the `id` and the phrase, then edit.
3. **Check:**
   - in the plugin's own folder, run `nix build --no-link`. The template's
     flake builds it with `mkCompanionPlugin`, which runs `plugins.py
     --check` (`nix/plugin.nix:19`), so no Nixi checkout is needed.
     `--no-link` matters: a `result` symlink in the folder is refused by
     the checker and scanner (`app/plugins.py:327`, `:1039`);
   - then do a real run:
     - install it as a folder plugin into
       `$XDG_DATA_HOME/nixi-companion/plugins/` (default
       `~/.local/share/...`);
     - in Settings → Plugins, turn it on. Only a stage plugin shows a
       consent prompt (`docs/GUIDE.md:490–491`, `:504–505`);
     - for a stage plugin: say its phrase and see the card;
     - for the other kinds: a prop or character is chosen in Settings →
       Look as `plug:<id>`. Then check that quips, the notification
       category or the reaction shows up.
   - The sandbox needs `bwrap`, plus `pasta` and `ip` when `network` is
     true. The skill gives the error lines to expect when they are missing.
   - **Private characters branch off before this step:** they stay a local
     folder with `chmod -R go=`, with no `--check`, no Nix and no publishing
     (`app/plugins.py:1036`, `docs/GUIDE.md:492–495`).
4. **Install** it with `services.nixi.companion.plugins` and
   `nixi.lib.<system>.mkCompanionPlugin`, or keep it as a folder plugin.
5. **Share it:**
   - in its own repo, using the template's `flake.nix`. That file declares
     `inputs.nixi.url = "github:olafkfreund/nixoarchy-snowflake"` and builds
     for the systems `nixi.lib` exports (x86_64-linux and aarch64-linux).
     Add the `nixi-plugin` topic;
   - users add it as a flake input and list
     `inputs.my-plugin.packages.<system>.default` in
     `services.nixi.companion.plugins`.

It also has a "never" list taken from the checker:
- `network` with `reads`;
- an `argv` path outside the folder;
- symlinks or hard links;
- `videos` (used only by `news`);
- skipping the SVG limits;
- committing a private character.

Each rule cites where it is enforced: its line in `plugins.py`, or
`docs/GUIDE.md:492–495` for private characters.

The skill describes behaviour only. The reference files hold the key
lists, so the test has one place to check.

### Template `run`

- A `#!/usr/bin/env python3` script, like the examples. The sandbox mounts
  `/usr/bin/env` but not `/bin/sh` (`app/plugins.py:664`).
- It prints one static JSON object:
  `{"v": 1, "kind": "facts", "title": …, "points": [two strings]}`. That is
  the schema `stages.py:138–150` accepts.
- No network and no extra data file. It is mode 0755 in git.

### The drift test (`tests/test_plugin_skill.py`)

It is a `unittest` test, like the other plugin tests:

1. `plugins.check_dir(template)` returns no error.
2. The template's `run` is executable. It runs through
   `plugins.run_stage(..., fresh=True)` in the sandbox, with an isolated
   `plugins.State` that has the template enabled at its current hash (the
   same fixture as `test_plugin_sandbox.py:25`). Like that test's `setUp`
   (`:47`), it patches `plugins.State` to return the isolated state, so it
   never reads the host's `plugins-state.json`. It returns the expected
   `points`.
   - It is skipped when `plugins.bwrap_ok()` is false. Under
     `NIXI_SANDBOX_TESTS=require` (the dev shell default) it fails
     instead.
3. The reference files hold **labelled tables**, one per field. Each table
   is checked against its own allowed set, so a valid reaction cannot pass
   as a category. This catches invalid names, not missing ones.
   - The tables are manifest keys, prop keys, character keys, stage keys,
     categories, reactions, round fits and `reads`.
   - The sets are `REQUIRED`/`OPTIONAL`, `PROP_KEYS`, `CHARACTER_KEYS`,
     `STAGE_KEYS`, `CATEGORIES`, `REACTIONS` and `ROUND_FITS`. The `reads`
     values are inline at `:217`, so the test lists them and cross-checks
     them with `_check` on a sample manifest.
   - The `reads` table also shows each feed's stdin fields, and notes that
     `phone` and `peers` may be absent.
4. No file under `skills/nixi-plugin/` is a symlink. `template/` has no
   `private` key.

A flake check is added next to the exported `broken-manifest-fails` check
(`flake.nix:137`, using the `mk` helper at `:82`):
`mk { pname = "nixi-plugin-template"; src = ./skills/nixi-plugin/template; }`.
It proves that the template builds with `mkCompanionPlugin`.


- `razer_home.nix` already takes `inputs`. `p620_home.nix` only needs

## Alternatives rejected

- **The template in `plugins/template/`.** Nixi would load it from a
  checkout (both reviews).
- **Teaching `scan()` to skip `template`.** That changes `app/plugins.py`
  and the sandbox test scope for no gain.
- **The skill in nixos_config.** It would drift from the code it describes,
  and other users would not get it.
- **A new `plugins.py --run` command.** The intent rules out runtime
  changes, and the folder install plus consent is the real path users take.
- **A plugin index file.** It needs upkeep; the topic is enough.
- **A test that the skill mentions every key.** It is too brittle for
  prose. Review covers new features.

## Risks

- **The skill goes stale when the plugin API grows.**
  - The test catches invalid names, not missing ones.
  - Mitigation: the reminder lives in the test's docstring and at the end
    of `SKILL.md`. No `app/plugins.py` change: `app/` is out of scope, and
    `plugins.py` is part of the `nixi-status` build.
- **The template's `flake.nix` has no tested build.** It references
  `nixi.lib.<system>.mkCompanionPlugin` as an input. The flake check builds
  the template's folder with the same function, but not through the
  template's own `flake.nix`.
  - Mitigation: the plan runs `nix build --no-link --override-input nixi path:<checkout>`
    once on a copy of the template. After the merge, it checks the
    published URL once, and records both results.
- **Rollout.** A wrong `source` path breaks home-manager evaluation on p620
  and razer. The plan builds both hosts' configs before the switch.
  - p510 still follows the `nixi-companion` bump (`nixi-status`). Building
    it needs the owner's OK, so the plan only *evaluates* p510's toplevel
    to confirm it still evaluates, and skips its build.
- **No runtime risk.** `app/` is not changed.
